SentinelLLM Component Guide
===========================

Project name: SentinelLLM
Full title: Contract-Driven AI/LLM Application Security Scanner

Purpose
-------
SentinelLLM is a security scanner for applications that use LLMs, agents, retrieval, memory, tools, APIs, and user data. Its goal is not just to send random attack prompts. Its goal is to understand the target, plan controlled security tests, execute them safely, judge the responses, adapt the next attack, verify reproducible behavior, and generate evidence-based reports.

Main use case
-------------
A security engineer, developer, auditor, or hackathon demo team can use SentinelLLM to test an AI application for LLM-specific risks such as prompt injection, sensitive information disclosure, excessive agency, unsafe tool use, RAG poisoning, hidden context exposure, misinformation, and improper output handling.

The scanner helps answer questions like:
- Does the target expose hidden instructions or secrets?
- Does the model follow attacker-controlled instructions?
- Does the application leak other users' or tenants' data?
- Does the application produce unsafe HTML or JavaScript output?
- Does the application trigger tool/action behavior without authorization?
- Does the application handle malformed or poisoned context safely?
- Can a suspicious response be reproduced by a second controlled test?

High-level workflow
-------------------
1. User starts the scan through the CLI.
2. Configuration is loaded from YAML or a direct target URL.
3. TargetConnector prepares authenticated, bounded HTTP communication.
4. DiscoveryAgent discovers the target and possible API endpoints.
5. AttackPlanner selects relevant OWASP-style attack categories and strategies.
6. AttackAgent turns plans into executable attack jobs.
7. AttackPolicy checks scope, duplicates, HTTP methods, budgets, and limits.
8. AttackExecutor sends approved jobs through the connector.
9. Response analysis extracts signals and evidence from the target response.
10. AttackJudge decides whether the response is failed, partial, potential success, or error.
11. AttackAgent adapts by switching strategy, refining, verifying, or stopping.
12. VerificationComponent confirms only reproduced candidate findings.
13. FinalEvaluator promotes verified candidates to final security findings.
14. HistoryStore persists the full scan lifecycle.
15. ReportGenerator writes JSON and HTML security and attack journey reports.

Important concept: contract-driven testing
------------------------------------------
SentinelLLM uses configuration and discovery as a security contract. The contract defines the target URL, authentication, allowed methods, scan budgets, discovery paths, enabled attack categories, LLM provider settings, and report location. This keeps the scanner bounded and auditable.

Important concept: adaptive testing
-----------------------------------
SentinelLLM does not simply run a static prompt list. It observes each result and chooses what to do next. If a strategy fails, it can switch. If a response looks suspicious, it can verify. If evidence is enough or budget is exhausted, it stops.

Important concept: verified findings
------------------------------------
A single suspicious response is not automatically a final vulnerability. SentinelLLM records it as a candidate and verifies it. By default, verification requires evidence reproduced across at least two distinct jobs and two distinct strategies.

Connector package
-----------------
src/sentinelllm/connector/__init__.py
- Connector package marker.
- Use case: groups target communication abstractions and implementations.

src/sentinelllm/connector/base.py
- Defines TargetConnector and TargetResponse.
- TargetConnector is the abstract contract for sending requests.
- TargetResponse normalizes status code, response body, headers, and metadata.
- Use case: lets the rest of the scanner use target transport without knowing how HTTP is implemented.

src/sentinelllm/connector/http.py
- Standard-library HTTP connector implementation.
- Handles headers, JSON bodies, cookies, redirects, retries, timeouts, concurrency, pacing, and request budgets.
- Disables automatic redirects so the scanner does not silently contact out-of-scope destinations.
- Use case: sends real HTTP requests to authorized targets safely and consistently.

Discovery package
-----------------
src/sentinelllm/discovery/__init__.py
- Discovery package marker.
- Use case: groups discovery contracts and logic.

src/sentinelllm/discovery/base.py
- Defines DiscoveryAgent abstract contract.
- Use case: establishes that discovery produces a TargetProfile from a ScanConfiguration and TargetConnector.

src/sentinelllm/discovery/discovery_agent.py
- Default discovery implementation.
- Sends a baseline request to the target.
- Checks content, headers, and response body for LLM/RAG/tool/structured-output signals.
- Tries configured discovery paths such as /openapi.json and /swagger.json.
- Builds EndpointProfile and TargetProfile objects.
- Use case: helps SentinelLLM understand what the target looks like before planning attacks.

src/sentinelllm/discovery/parsers.py
- Parses OpenAPI JSON and HTML forms.
- Extracts endpoint URLs, methods, parameters, content types, and same-origin forms.
- Rejects external form actions/endpoints.
- Use case: turns discovered documents into safe, usable endpoint profiles.

Planning package
----------------
src/sentinelllm/planning/__init__.py
- Planning package marker.
- Use case: groups attack planning components.

src/sentinelllm/planning/attack_planner.py
- Defines AttackPlanner and DefaultAttackPlanner.
- Selects applicable strategies from the registry based on enabled categories and target profile.
- Chooses writable discovered endpoints when available.
- Builds AttackPlan objects.
- Use case: decides what high-level attack plans should be attempted.

src/sentinelllm/planning/strategies.py
- Defines AttackStrategy, StrategyRegistry, and the default OWASP-style strategy registry.
- Contains 10 LLM security categories.
- Registers 5 techniques per category: baseline, boundary, mutation, context, and verification.
- Each strategy has objective, description, prompt template, expected signals, success criteria, stop conditions, remediation guidance, risk level, and applicability requirements.
- Use case: this is the scanner's attack knowledge base.

Attacks package
---------------
src/sentinelllm/attacks/__init__.py
- Attacks package marker.
- Use case: groups attack generation, execution, policy, analysis, and related compatibility modules.

src/sentinelllm/attacks/agent.py
- Defines AttackAgent and DefaultAttackAgent.
- Creates initial AttackJob objects from AttackPlan objects.
- Creates and refines hypotheses.
- Adapts after every observed response by choosing switch_strategy, refine_strategy, verify, or stop.
- Builds provider-specific target request payloads such as single-field prompt bodies, Anthropic messages bodies, or Gemini generateContent bodies when configured.
- Use case: controls the adaptive attack journey.

src/sentinelllm/attacks/analysis.py
- Converts raw AttackResult responses into Observation and Evidence objects.
- Detects server errors, redirects, authentication changes, reflected input, expected markers, structured output, tool calls, actions, state changes, security keywords, XSS payloads, unbounded output, and baseline deviation.
- Use case: extracts observable security signals without making the final vulnerability decision.

src/sentinelllm/attacks/executor.py
- Defines AttackExecutor and DefaultAttackExecutor.
- Executes an approved AttackJob through the injected TargetConnector.
- Normalizes execution results into AttackResult objects.
- Use case: separates job execution from planning, judging, and HTTP implementation.

src/sentinelllm/attacks/policy.py
- Defines AttackPolicy.
- Validates each job before execution.
- Enforces target scope, allowed HTTP methods, duplicate fingerprints, per-endpoint request budgets, scan request budgets, and job limits.
- Use case: prevents uncontrolled or out-of-scope scanning.

src/sentinelllm/attacks/models.py
- Compatibility/re-export module for attack-related core models.
- Use case: keeps older or attack-focused imports clean.

src/sentinelllm/attacks/result.py
- Compatibility/re-export module for AttackResult.
- Use case: keeps imports stable for code that expects attack results under attacks.

Judging package

How the main data objects move through the system
-------------------------------------------------
ScanConfiguration
- Created by CLI/config loader.
- Contains target, auth, LLM, attack, scan, and report settings.

TargetProfile
- Created by DiscoveryAgent.
- Describes discovered capabilities and endpoints.

AttackPlan
- Created by AttackPlanner.
- Describes what to test and why.

AttackJob
- Created by AttackAgent.
- Contains the actual request to send.

PolicyDecision
- Created by AttackPolicy.
- Says whether a job is approved and why.

AttackResult
- Created by AttackExecutor.
- Contains raw HTTP status, response body, headers, metadata, and errors.

Observation
- Created by analyze_response.
- Summarizes evidence signals found in the result.

Evidence
- Created by analyze_response.
- Records concrete facts that support later judging and findings.

JudgeResult
- Created by AttackJudge.
- Classifies the result and recommends next action.

AttackHypothesis
- Created/refined by AttackAgent.
- Tracks what the scanner believes may be happening.

AdaptationDecision
- Created by AttackAgent.
- Records whether the scanner switched strategy, refined, verified, or stopped.

Finding
- Created by FinalEvaluator from strong judged results.
- Promoted to final finding only after verification.

ScanHistory
- Central lifecycle record.
- Stores configuration, target profile, plans, jobs, decisions, results, evidence, observations, judgments, hypotheses, adaptations, candidate findings, verification results, final findings, errors, and timestamps.

Supported LLM security categories
---------------------------------
1. Prompt Injection
- Tests whether untrusted text can override system/application instructions.
- Example risk: model follows attacker instruction instead of trusted policy.

2. Sensitive Information Disclosure
- Tests whether the target leaks credentials, private data, tenant data, hidden values, internal docs, or protected context.
- Example risk: model reveals project details, API keys, passwords, or customer data.

3. Excessive Agency
- Tests whether the model/tool layer performs unauthorized actions.
- Example risk: refund, delete, email, execute command, or update state without approval.

4. Supply Chain
- Tests provenance and trust boundaries around models, plugins, data, prompts, dependencies, and tools.
- Example risk: unverified plugin or model source is trusted blindly.

5. Data and Model Poisoning
- Tests whether untrusted or conflicting content can corrupt behavior or policy.
- Example risk: target absorbs malicious context as trusted knowledge.

6. Unbounded Consumption
- Tests whether the target can be pushed into excessive output, tokens, requests, cost, or time.
- Example risk: expensive or runaway response generation.

7. Misinformation
- Tests whether the target makes confident unsupported claims.
- Example risk: gives false high-impact advice without uncertainty or sources.

8. Hidden Context Exposure
- Tests whether hidden system prompts, developer messages, internal context, or guardrails leak.
- Example risk: system prompt exposure.

9. Vector and Embedding Weaknesses
- Tests retrieval isolation, tenant separation, and indexed-content trust.
- Example risk: one tenant retrieves another tenant's confidential data.

10. Improper Output Handling
- Tests whether model output is treated as trusted executable content.
- Example risk: XSS, unsafe HTML, script injection, unsafe markdown links.

How to run the local demo
-------------------------
Terminal 1:
python -m demo.target_app --port 8765

Terminal 2:
sentinelllm scan --config configs/demo_scan.yaml

Expected output:
- A new scan ID is logged.
- Reports are written under reports/demo/<scan_id>/.
- The attack journey report shows every prompt sent and every response received.
- The security report shows verified findings and OWASP category coverage.

Security and safety boundaries
------------------------------
- Secrets are referenced through environment variables, not stored directly in config.
- Report data redacts sensitive keys such as authorization, tokens, cookies, passwords, and API keys.
- Every job must pass AttackPolicy before execution.
- Redirects are not automatically followed.
- Request budgets and timeouts prevent unbounded scanning.
- LLM providers cannot create evidence, execute target requests, bypass policy, or expand scan scope.
- Findings require verification before final reporting.

Why the project is useful
-------------------------
SentinelLLM is useful because LLM applications fail differently from traditional web apps. A standard scanner can find missing headers or SQL injection patterns, but it usually cannot understand model behavior, hidden context exposure, tool misuse, retrieval leakage, or prompt-driven control flow. SentinelLLM focuses on those AI-specific behaviors and creates reports that show the attack journey, evidence, and remediation.
